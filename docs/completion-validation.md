# 1.0.4 완료 상태 수정 및 검증 — NO-GO

## 실제 사용자 결과와 원인 분석

[1.0.3 사용자 보고](completion-user-report.md): 설치·탭 탐색·시험 알림음·파비콘 교체 PASS, 답변 종료 후 녹색 대신 회색 대기 표시 FAIL. 실제 사이트 전이 로그나 화면 DOM이 없어 **해당 사용자의 단일 원인은 확정하지 못했습니다**. 시험 알림음 PASS는 실제 완료 자동 알림을 뜻하지 않습니다.

코드 검토로 확인된 가능성:
1. 1.0.3에서는 사용자 제출이 페이지 내부 감지기에만 남고 Worker에는 생성 중지 버튼이 관찰된 후 시작 이벤트가 전달됩니다. 제출은 감지됐지만 Stop 신호가 누락되거나 빠르게 지나가면 Worker는 `IDLE`에 남을 수 있습니다.
2. 응답의 첫 assistant 요소가 Stop 관찰 이전에 삽입되고 그 후 변화가 관찰되지 않으면 완료 후보에 필요한 응답 변화 신호가 빠질 수 있습니다. 복사 버튼·입력창·도구 활동 선택자 변경 역시 완료 누락의 가능성입니다.
3. 1.0.3의 Worker에서 이미 `COMPLETED`인 상태는 `IDLE` 이벤트만으로 대기로 바뀌지 않지만, 같은 대화의 `RESET`은 완료를 `UNKNOWN`으로 지웠고 이후 `IDLE`이 들어올 수 있었습니다. 실제 사용자에게 이 경로가 발생했는지는 미확인입니다.

## 수정한 상태 계약

- 제출 클릭/Enter는 **제출 의도**로 기록합니다. 생성 시작 신호가 없으면 기존 대기 상태를 `UNKNOWN`으로 바꾸되, 기존 완료 상태는 그대로 보존합니다. 제출 의도만으로 작업 중이나 완료로 추측하지 않습니다.
- 같은 문서·경로에서 제출 후 Stop이 관찰되어야 새 작업 ID를 발급하고 `PROCESSING`으로 전환하며 미확인 완료를 초기화합니다. 제출 의도는 120초 후 만료됩니다(백그라운드 타이머에 따라 화면 반영이 지연될 수 있음). Stop을 놓친 빠른 응답은 여전히 완료 판정하지 않습니다.
- 제출 시점의 assistant 요소 수를 메모리에서 비교해 Stop 관찰 직전 추가된 새 응답 요소를 감지합니다. 본문은 저장하지 않습니다. 기존 답변 변화, Stop 소실, composer, 최종 제어, 도구 활동, 안정화 구간을 함께 확인하며 신호가 부족하면 완료로 바꾸지 않습니다. 요소 가상화나 UI 변경으로 오탐·누락 가능성은 남습니다.
- 확인된 `COMPLETED`와 `unread`는 독립 관리합니다. 같은 `/c/…` 대화의 RESET, IDLE 및 탭 중단에서 완료 상태와 미확인을 보존합니다. 탭 확인은 `unread`만 해제하며 상태는 새 요청의 시작이 확인될 때까지 완료로 남습니다. 다른 대화로 이동하면 완료를 이어받지 않습니다. 일시적으로 감지가 중단된 완료 항목에는 별도 표시가 붙습니다.
- 완료 미확인 중 별도 오류/제한 UI를 감지하면 녹색 완료는 보존하되 대시보드에 별도 오류 신호를 표시하고 알림을 한 번 요청합니다. 이 오류도 UI 기반이므로 오래된 alert에 의한 오인 가능성이 있습니다.
- 같은 작업의 반복 완료 이벤트는 상태를 재완료하거나 알림을 다시 요청하지 않습니다. Worker 저장 직후·알림 호출 전 종료되면 알림이 누락될 수 있고, 여러 탭에 열린 동일 대화의 중복은 제거하지 않습니다.
- 대시보드의 각 탭 **진단**은 최근 Worker 전이·사유와 현재 페이지의 감지 단계·불충분한 신호를 보여줍니다. Worker 이력은 탭별 최근 30개를 로컬에 저장하고, 페이지 이력은 현재 페이지 메모리에 최대 50개 유지하며 각각 화면에는 최근 12개를 표시합니다. 제목·URL·본문은 이력 항목에 포함하지 않지만 시각은 민감할 수 있습니다. **진단 로그 → 로그 삭제**로 이력을 지울 수 있으며, 주입되지 않은 탭의 페이지 이력은 탭 새로고침이 필요할 수 있습니다.

## 사용자 재시험

1. 1.0.4 ZIP을 풀어 기존 압축해제 확장 폴더에 덮어쓰고 `chrome://extensions`에서 확장을 새로고침한 뒤 **ChatGPT 탭도 새로고침**합니다. 확장을 삭제하면 로컬 설정이 삭제될 수 있습니다.
2. 기존 대화와 새 대화에서 각각 실제 요청을 제출합니다. 제출 직후 및 생성 중에 해당 탭 **진단**을 눌러 `SUBMIT`, `OBSERVE_ACTIVE`, `STOP_NOT_OBSERVED` 등의 이력을 확인합니다. 파비콘 강제 시험이 켜져 있다면 먼저 종료합니다.
3. 실제 응답 종료 후 진단을 다시 눌러 `FINISH`와 `STABLE_FINAL_EVIDENCE`, Worker 상태 `COMPLETED`, 녹색 아이콘 및 실제 자동 알림을 확인합니다. 로그에 `FINAL_CONTROL_NOT_FOUND`, `ASSISTANT_CHANGE_NOT_OBSERVED`, `TOOL_OR_BUSY_SIGNAL` 등이 있다면 해당 신호가 완료를 막고 있는 것입니다.
4. 미확인 상태에서 다른 탭에 두고 기다린 뒤 같은 대화를 새로고침해 녹색과 미확인이 유지되는지 확인합니다. 해당 탭을 열어 읽음 처리 후 새 요청을 제출하고 실제 생성 시작 신호가 나타날 때만 작업 중으로 바뀌는지 확인합니다. 중단, 오류, 도구 호출 중간 응답과 중복 알림도 별도 검증합니다.
5. 이력을 공유할 때 시각이 민감할 수 있으므로 검토하고 대화 제목·URL·본문·계정 정보가 포함된 화면은 공유하지 마세요.

녹색은 현재 UI 휴리스틱이 완료라고 판단한 상태이지 실제 답변의 정답이나 서비스 종료를 보증하지 않습니다. 실제 로그인 환경과 Windows에서 이 수정이 검증될 때까지 출시 판정은 **NO-GO**입니다.
